# Plan Mode Capability v1

## 1. 能力定位

Plan 模式是 Dennis Risk Agent 的主 Agent 编排层能力。

Plan 是执行前计划，不是真实查询结果。Plan 不调用真实接口，不生成 observation，不下结论。它的作用是把用户的复杂问题转译成“用户能看懂、可选择、可确认”的研判计划。

核心口径：

> Plan 模式是复杂研判前的解释层，不是所有查询的前置流程；执行模式才是真正调用手脚查数据。

重要边界：

- Plan 不是所有问题的默认前置流程。
- 真实研判问题默认进入执行模式。
- Plan 只在用户显式要计划，或边界不清、批量扩展、高风险动作不适合直接执行时触发。
- 当前项目尚未完成正式安全执行框架；本文件只沉淀 Plan 的只读边界和待确认动作，不实现安全执行框架。

## 2. Plan 模式与执行模式的区别

### Plan 模式

用于查询前说明：

- 我理解的问题。
- 本次研判目标。
- 查询路径与强区分证据卡。
- 证据强弱说明。
- 查询边界。
- 预期输出。
- 用户选择项。

Plan 不做：

- 不查真实数据。
- 不生成 observation。
- 不输出最终风险结论。
- 不承诺处置动作。
- 不伪造证据。

### 执行模式

用于真实查询和研判：

- 识别实体。
- 路由能力。
- 调用平台手脚。
- 收集 observation。
- 输出研判结论。
- 给出强 / 中 / 弱证据分层和反证。

执行模式适合：

- 用户明确要“看下 / 查下 / 判断一下”。
- 实体明确。
- 查询范围可控。
- 低风险只读查询。
- 不涉及大批量扩展或处置动作。

执行模式可以在开头用一句轻量说明：

```text
我会先看基础画像、登录变化、设备可信度和策略命中，再按强/中/弱证据给结论。
```

但不应只输出 Plan 阻断用户获取结果。

## 3. 触发条件

### 强制触发 Plan

- 用户明确说“先给我计划 / 先说怎么查 / 查之前说下思路 / 先不要执行”。
- 用户问“这个要怎么查比较合理”。
- 用户要求“设计排查路径”。
- 批量规模较大。
- 需要用户确认是否做关联扩展。
- 实体缺失或实体类型不明确。
- 候选实体可能过多。
- 涉及写操作、处置动作、敏感字段、越权路径。
- 用户问题明显是方法论，不是要真实查询结果。

### 默认进入执行模式

- “帮我看下这个用户是不是风险用户”。
- “这个账号是不是盗号”。
- “这批账号是不是一伙的”。
- “这个用户是不是误伤”。
- “这个 request_id 为什么被拦”。
- “这个 device_id 有没有问题”。
- “查一下 user_id=xxx”。
- “看下 device_id=xxx 的风险标签”。
- “直接看 request_id=xxx 命中了什么策略”。

这些问题可以轻量说明执行思路，但不应只输出 Plan 阻断用户获取结果。

### 不触发 Plan

- 用户只是问概念解释。
- 用户只是问某个平台能力说明。
- 用户只要求改写文案、总结材料。
- 单一平台、单一字段、低风险只读查询。
- 用户明确说“不用计划，直接查”。

## 4. Plan 标准输出结构

```text
## 研判计划

### 1. 我理解的问题
用一句话复述用户想解决的问题，避免直接照抄用户原话。

### 2. 本次研判目标
- 是否存在明确风险迹象。
- 风险更像哪一类：盗号 / 群控 / 设备异常 / 策略误伤 / 业务正常行为。
- 哪些证据支持风险，哪些证据支持正常或误伤。
- 目前是否存在证据不足，不能直接下结论。

### 3. 查询路径与强区分证据卡
| 步骤 | 查询内容 | 使用能力 | 重点寻找的强区分证据 | 命中后说明什么 |
|---|---|---|---|---|
| 1 | 用户基础画像 | 档案中心 | 账号状态异常、历史处罚、活跃习惯断裂 | 判断账号是否存在基础风险，或是否有正常反证 |
| 2 | 登录变化 | 登录统一日志 | 新设备登录、异地突变、失败重试后成功、登录习惯断裂 | 更像盗号、接管或异常登录链路 |
| 3 | 设备可信度 | 设备 SDK / 设备画像 | root、hook、frida、模拟器、代理、多开、多账号共用 | 说明设备环境不可信，或存在批量控制可能 |
| 4 | 策略命中解释 | 天狮 / 策略平台 | 命中策略与异常行为时间强一致，命中原因可解释 | 解释为什么被拦，以及拦截是否合理 |
| 5 | 正常反证 | 多源综合 | 历史稳定、设备连续、行为自然、无处罚、无高危关联 | 支持误伤、正常用户或证据不足判断 |

### 4. 证据强弱说明
- 强区分证据：命中后对结论影响最大，例如习惯断裂、高风险设备、多账号聚集、策略命中与异常行为强一致。
- 中等辅助证据：能增强判断，但不能单独下结论，例如单次异地、轻量策略命中、短期活跃波动。
- 弱证据 / 噪声证据：只能提示关注，不能作为主要结论，例如单条低置信关联、单次异常、无上下文命中。
- 正常反证：用于支持误伤、正常用户或证据不足判断，例如历史稳定、设备连续、行为自然、无处罚记录。

### 5. 查询边界
- 只做只读查询，不做处置动作。
- 不默认批量扩展关联账号 / 关联设备。
- 关联关系只作为候选证据，不直接等于作弊结论。
- 单点证据不能直接定性。
- 需要多证据闭环才能增强结论置信度。
- 如果候选过多，返回 too_many_candidates，不继续深查。
- 如果关键实体缺失，返回 missing_user_id / missing_device_id / missing_request_id 等缺失原因。
- 如果平台权限或认证态不足，返回 permission_blocked / auth_required / path_error 等状态，不伪造结果。
- 当前项目尚未完成正式安全执行框架，因此 Plan 只能表达只读边界和待确认动作，不能承诺已经具备完整安全拦截能力。

### 6. 预期输出
- 结论摘要。
- 关键证据 3-5 条。
- 风险类型判断。
- 强证据 / 中证据 / 弱证据 / 反证分层。
- 缺失证据。
- 证据置信度和质量风险。
- 下一步建议。

### 7. 你可以选择
A. 按默认计划执行
B. 缩小范围，只查基础信息
C. 加强设备 / 关联 / 批量风险分析
D. 先不要执行，只优化计划
```

注意：

- “查询路径与强区分证据卡”必须使用合并表格，不拆成两个重复模块。
- 具体行要根据用户问题裁剪，不要每次机械输出全部能力。
- 面向半开放用户时，减少内部平台名堆叠，多解释“为什么查这些证据”。

## 5. 执行模式中的证据卡要求

证据卡不只属于 Plan 模式。真实执行模式最终输出也应该有证据强弱分层。

执行模式推荐输出：

- 结论摘要。
- 关键证据 3-5 条。
- 强区分证据。
- 中等辅助证据。
- 弱证据 / 噪声证据。
- 正常反证。
- 缺失证据。
- 下一步建议。

也就是说：

- Plan 模式有“查询路径与强区分证据卡”。
- 执行结果有“证据强弱分层”。

## 6. 场景化证据卡要求

### 用户风险研判

重点证据卡：

- 用户基础画像卡。
- 账号历史变化卡。
- 登录异常链路卡。
- 设备可信度卡。
- 策略命中解释卡。
- 正常反证卡。

### 设备风险研判

重点证据卡：

- 设备可信度卡。
- 设备环境异常卡。
- 设备到用户关联卡。
- 多账号共用卡。
- 设备风险标签卡。
- 正常反证卡。

### ATO / 盗号研判

重点证据卡：

- 账号习惯断裂卡。
- 新设备登录卡。
- 异地 / 异常登录卡。
- 登录失败后成功卡。
- 高风险设备登录卡。
- 历史稳定反证卡。
- 登录日志窗口限制提示卡。

ATO / 登录日志类 Plan 和执行结果都必须说明：

在线统一登录日志可能存在窗口限制。超出在线日志窗口后，无登录记录 / 无异常登录记录不能直接作为“没有盗号 / 没有异常登录”的强反证。需要标注 `login_log_window_incomplete` / `offline_hive_required` 等缺口。

### request_id / 策略命中解释

重点证据卡：

- 策略命中解释卡。
- 命中时间与行为匹配卡。
- 请求上下文卡。
- 用户 / 设备补证卡。
- 误伤反证卡。

### 群控 / 批量作弊研判

重点证据卡：

- 多账号聚集卡。
- 设备共用卡。
- 行为节奏相似卡。
- 关联实体风险卡。
- 批量注册 / 批量登录 / 批量操作卡。
- 候选过多保护卡。

### 误伤判断

重点证据卡：

- 正常历史卡。
- 设备连续卡。
- 行为自然卡。
- 策略命中孤立性卡。
- 无处罚 / 无高危关联反证卡。

## 7. 输出原则

- Plan 不是结论。
- Plan 不是查询结果。
- Plan 不能伪造证据。
- Plan 不能把候选关联直接定性为作弊。
- Plan 的用户体感要强，尽量用业务语言解释，不要只写内部字段名。
- Plan 要短而清晰，避免文档味过重。
- Plan 要帮助用户理解“为什么这么查”。
- Plan 要为未来安全执行框架预留边界字段，但本轮不要实现安全执行框架。
- 不要把所有真实研判问题都前置 Plan，否则用户会觉得啰嗦。
- 对真实研判问题，默认执行；对显式计划请求或边界不清问题，才 Plan。
