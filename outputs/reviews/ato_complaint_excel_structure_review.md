## 5. 哪个表适合做高质量回归 case

优先：`工作表2`

原因：
- 77 条均有 user_id、核查日期、用户自述、用户自述被盗日期、是否盗号。
- 大部分有被盗日期、盗号大类、盗号小类、作恶类型。
- 覆盖地推欺诈、钓鱼欺诈、短信泄露、token 泄露等典型 ATO 路径。
- 用户自述链路完整，适合沉淀成正例回归。

限制：
- 全部为“是”，缺少反例和不确定样本。
- 核查人、是否新增case、是否回捞等结构字段为空，回捞信息混在“盗号具体原因”。

## 6. 哪个表适合作历史样本池 / 待清洗样本池

优先：`工作表1`

原因：
- 样本量大，包含 662 个有效 user_id。
- 覆盖正例、否、不确定、历史 case、空标签、非被盗、反诈封禁、导流封禁、实名租借、历史群控误伤等边界。
- 适合用于反例、不确定样本、标签缺失样本和清洗规则回归。

限制：
- `是否盗号` 有 105 条空值。
- `盗号大类 / 小类 / 作恶类型` 空值多。
- `是否回捞` 字段混入备注，例如“钓鱼软件”“同某 case”“4月9日又登录某来源”等，不是纯布尔字段。
- `回捞量级` 全空，无法支持回捞规模分析。

## 7. 数据质量问题

| 问题 | 影响 |
|---|---|
| `是否盗号` 存在空值 | 不能直接用于正负样本训练或回归期望 |
| `盗号大类 / 小类` 空值较多 | 需要保留为标签缺失，不应自动补类 |
| `作恶类型` 大量为空 | 下游发布内容类型证据不完整 |
| `是否回捞` 在工作表1混入备注文本 | 需要拆成 `is_resweep` 与 `resweep_note` |
| `盗号具体原因` 同时承载原因、回捞、来源、历史信息 | 后续需要结构化抽取 |
| 工作表2 `核查人 / 是否新增case / 是否回捞` 全空 | 无法从结构字段判断复核责任和回捞状态 |
| `info` 仅提示内部文档 | 不应进入样本资产 |

## 8. 建议资产化方式

| 资产 | 来源 | 用途 |
|---|---|---|
| 高质量正例回归 | 工作表2 | ATO 正例链路验证 |
| 反例 / 证据不足回归 | 工作表1 | 防止因申诉、发布、地区不一致强判 |
| 标签清洗样本 | 工作表1 | 标签标准化和字段质量回归 |
| 回捞状态样本 | 两表的“盗号具体原因” | Data Agent 匹量验证 |
| Data Agent query_intent 样本池 | 两表 | 后续批量取数验证 |
