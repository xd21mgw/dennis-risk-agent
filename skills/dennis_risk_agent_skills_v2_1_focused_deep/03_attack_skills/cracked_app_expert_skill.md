# Cracked App Expert Skill：破解包治理 Skill v2.3 executable-deep

## 0. Skill 定位

本 Skill 解决“客户端是否被改造、破解包如何补证、如何治理”的问题。破解包是被改造的客户端，不是协议；但破解包可能去 SDK、绕采集、替换安全模块或动态加载插件，从而制造“像协议”的端侧证据缺失。

不解决：无客户端工件证据、纯接口直打的单纯协议问题；完整官方包但统一调度的群控问题；官方包埋点缺失或数据口径问题。遇到这些情况应切换或组合 protocol_attack_expert_skill、group_control_expert_skill、plugin_reverse_analysis_skill、risk_governance_design_skill。

## 1. 触发条件

- 关键词触发：破解包、改包、二开包、盗版包、非官方包、包签名异常、SDK 缺失、采集异常、hook、root、动态加载、dex/so/assets 异常、安全模块替换。
- 业务场景触发：前端无日志但服务端有请求、端侧 SDK 日志覆盖率异常、同包名不同签名、外部分发渠道样本、官方版本对比异常、关键接口请求来自异常包。
- 用户意图触发：用户问“是不是破解包”“为什么像协议但有设备身份”“前端无日志是否协议”“怎么区分破解包/协议/群控/插件”。
- 反向不触发：
  - 无端行为且无任何包工件证据时，不强触发破解包，优先协议补证。
  - 官方包版本也缺日志时，不强触发破解包，优先埋点缺失或口径问题。
  - 端行为完整但批量调度明显时，不强触发破解包，优先群控。
- 需要转交给其他 Skill 的情况：
  - 无端链路、接口直达、签名/token/参数异常，且无包证据：protocol_attack_expert_skill。
  - 端行为存在但统一调度、设备/路径/收益成团：group_control_expert_skill。
  - 插件、辅助功能、动态加载工件明确：plugin_reverse_analysis_skill 或混合攻击分支。
  - 官方版本埋点缺失：数据口径/埋点治理分支。

## 2. 输入格式

- 必需输入：业务场景、异常请求或异常端日志、包签名/版本/渠道/SDK 日志中至少两类证据、当前处置目标。
- 可选输入：apk/aab 样本、包名、签名摘要、versionCode/versionName、渠道号、Manifest、权限、导出组件、dex/so/assets diff、安全模块版本、runtime 前台 activity、截图、行为轨迹、方法级短链证据、外部分发链接。
- 缺失时可默认假设：用户只问概念时，默认输出破解包本质、边界和最小补证动作。
- 缺失但不可假设时如何处理：缺少包样本、包签名或 SDK 覆盖率时，不定性破解包，只输出工件补证清单。
- 用户只给模糊问题时的最小可用输入：是否有包样本、包签名是否异常、SDK 日志是否缺失、异常请求是否能关联到版本/渠道/设备。

## 3. 专家认知

- 这类风险的本质：破解包通过改造客户端，绕过平台预期的采集、签名、验证、展示、权限或安全模块，让服务端看到的请求链路不完整、不可信或被伪装。
- 黑产 / 风险动机：绕过风控 SDK、去广告/解锁功能、伪造设备环境、绕过展示限制、降低自动化成本、为协议/群控/插件提供端侧外壳。
- 主要风险形态：
  - 去 SDK / 去采集破解：端行为存在但 SDK 日志缺失。
  - 安全模块替换：验签、加密、设备指纹或风控模块被替换。
  - 签名 / 参数绕过破解：包内改造参数生成或复用签名。
  - 功能解锁 / 展示改造：绕过权限、展示、广告或内容限制。
  - 注入插件破解：动态加载 dex/so/assets 或辅助功能。
  - 自动化辅助破解：前台 activity 和截图像正常端，但行为由脚本/插件驱动。
- 常见混合形态：破解包 + 协议直达、破解包 + 群控、破解包 + 插件、破解包 + 真人验证、破解包 + token 复用。
- 和相近风险的区别：
  - 单纯协议：没有可信端工件或端行为，重点是接口脱端；破解包有客户端工件异常或采集/安全模块被改造。
  - 官方包埋点缺失：官方签名、版本、渠道正常，多个正常版本同样缺日志，优先采集口径问题。
  - 群控真机：官方包和端采集可信，但设备/路径/收益被统一调度。
  - 插件辅助：插件可以附着在官方包或破解包上，若存在动态加载或辅助功能证据，需作为混合攻击处理。

## 4. 判断规则

按顺序判断，命中即进入对应分支；证据不足时不得强结论。

1. 如果无前端日志或 SDK 日志缺失，且包签名、版本/渠道、SDK 模块、安全模块、dex/so/assets 任一工件异常，则优先进入破解包判断，不直接判协议。
2. 如果服务端无端行为、接口序列异常、强目标接口直达，但没有包签名、SDK、版本、渠道或样本证据，则进入协议补证，不强判破解包。
3. 如果官方签名、官方版本、官方渠道也同样缺日志或采集异常，则优先考虑官方包埋点缺失、SDK 采集口径、网关采样或版本灰度问题。
4. 如果端行为存在且 SDK 日志可信，但同批启动/停止、路径节奏一致、设备/账号/收益成团，则进入群控判断。
5. 如果存在插件、辅助功能、动态加载 dex/so/assets、hook、root、脚本控制或外挂 UI，则进入插件辅助或破解包 + 插件混合攻击判断。
6. 如果包签名异常、同包名不同签名、非官方渠道分发、Manifest/权限/导出组件异常，且风险请求集中来自该类包，则判断为中高置信破解包，需要补运行时和方法级证据。
7. 如果安全模块被替换、SDK 缺失、方法级短链证明关键安全/采集方法被绕过，且风险请求与异常包闭合，则判断为高置信破解包。
8. 如果只有前端无日志、低质账号、IP 聚集、接口 QPS 上升，而无包工件证据，不得定性破解包，只能多分支补证。
9. 如果存在官方测试包、灰度包、企业内部分发、渠道包差异、采集降级、兼容性问题等反证，则必须降级或转授权/埋点治理。

## 5. 证据体系

- 强证据：
  - 包签名异常或同包名不同签名；
  - 非官方版本 / 渠道与风险请求闭合；
  - SDK 缺失、SDK 日志覆盖率异常且官方版本正常；
  - 安全模块、风控模块、验签模块被替换；
  - dex / so / assets 与官方包存在风险 diff；
  - Manifest 权限、导出组件、provider/service/receiver 异常；
  - runtime 前台 activity、截图、行为与服务端请求不一致；
  - 方法级短链证据证明采集、验签、设备指纹或风控方法被绕过；
  - 外部分发样本与内部风险设备/账号命中闭合。
- 中证据：
  - 某版本/渠道 SDK 日志覆盖率异常；
  - 风险请求集中于少数版本、渠道、签名或分发来源；
  - 官方包对比存在可疑 dex/so/assets 增删；
  - 设备身份存在但端采集链不完整；
  - 前台 activity 正常但关键 SDK 事件缺失；
  - 非官方渠道下载量或黑市样本出现。
- 弱证据：
  - 前端无日志；
  - 高频请求；
  - 低质账号；
  - IP 聚集；
  - UA/版本相似；
  - 单接口 QPS 上升。
- 反证：
  - 官方包版本也缺日志；
  - 埋点缺失、SDK 升级、采集口径变化；
  - 网关采样、端日志延迟、版本灰度；
  - 官方测试包、企业内部分发、合法渠道包；
  - 单纯协议无端链路；
  - 群控真机统一调度；
  - 插件独立注入但包本体正常。
- 误判来源：灰度版本未接 SDK、旧版本兼容问题、渠道包配置差异、弱网导致日志延迟、测试包未登记、网关采样缺失。
- 最小补证清单：
  - 包签名分布；
  - 版本 / 渠道分布；
  - Manifest / 权限 / 导出组件；
  - dex / so / assets diff；
  - SDK 缺失和端 SDK 日志覆盖率；
  - 安全模块是否被替换；
  - runtime 前台 activity / 截图 / 行为；
  - 方法级短链证据；
  - 官方版本对比；
  - 风险请求与异常包关联；
  - 设备 / 账号 / 行为 / 收益关联。

## 7. 治理闭环

- 查数补证：
  - 包签名分布；
  - 端 SDK 日志覆盖率；
  - 官方版本对比；
  - 风险请求与异常包关联；
  - 设备 / 账号 / 行为 / 收益关联；
  - 外部分发样本与内部风险设备/账号回连。
- 识别策略：异常签名、异常版本/渠道、SDK 缺失、安全模块替换、dex/so/assets diff、Manifest 异常、runtime 行为异常。
- 分层处置：
  - 高准：风险版本限制、强制升级、关键接口拒绝、设备/账号联动处置。
  - 中准：关键接口 step-up、限权、限速、加采、人工复核。
  - 低准：监控、样本采集、外部分发监测、版本审计。
- 治理动作：
  - 包完整性校验；
  - 签名校验；
  - 强制升级；
  - 风险版本限制；
  - 关键接口依赖端侧上下文；
  - 外部分发监测；
  - 样本库回流；
  - 与协议/群控/插件策略联动。
- 业务协同：客户端发版、渠道包管理、灰度版本登记、测试包白名单、兼容性评估、客服解释口径。
- 体验 / 误伤控制：官方灰度包、企业包、测试包和合法渠道包登记；风险版本先限制敏感接口，不直接影响低风险浏览。
- 指标评估：破解包发生量、异常签名数、异常版本/渠道数、SDK 覆盖率、风险接口占比、强制升级成功率、误伤率、客诉、迁移到协议/群控/插件比例。
- 样本回流和复盘：逆向样本库、签名黑白名单、版本风险库、方法级短链库、外部分发监测库、混合攻击样本回流到 protocol/group_control/plugin 策略。

## 8. 禁止行为

- 禁止把破解包直接等同协议。
- 禁止因为前端无日志 / SDK 缺失 / 采集异常直接判协议，必须检查破解包可能性。
- 禁止没有包签名、版本、SDK、工件或样本证据时强判破解包。
- 禁止忽略官方包埋点缺失、采集口径、灰度版本、测试包、合法渠道包反证。
- 禁止只做封禁，不做包完整性、强制升级、版本限制和外部分发监测。
- 禁止编造包名、签名、方法名、字段名或逆向结论。

## 9. 质量校验

输出前自查：

- 是否说明破解包不是协议，但会制造像协议的端侧证据缺失？
- 是否区分单纯协议、破解包绕采集、官方包埋点缺失、群控真机、插件辅助？
- 是否列出包签名、版本/渠道、Manifest/权限/导出组件、dex/so/assets、SDK 缺失、安全模块替换、runtime 前台 activity/截图/行为、方法级短链证据？
- 是否给出包签名分布、端 SDK 日志覆盖率、官方版本对比、风险请求与异常包关联、设备/账号/行为/收益关联等查数动作？
- 是否给出包完整性校验、强制升级、风险版本限制、关键接口端侧上下文、外部分发监测、样本库回流、协议/群控/插件联动？
- 是否列出官方包埋点缺失、灰度包、合法渠道包、单纯协议、群控真机、插件独立注入等反证？
- 是否有灰度、误伤控制和指标评估？

不合格时必须补齐后再输出。

## 10. 失败处理

- 信息不足：降级为“疑似破解包或端采集异常”，列包签名、版本/渠道、SDK 覆盖率和官方版本对比补证。
- 证据冲突：输出单纯协议、破解包绕采集、官方包埋点缺失、群控真机、插件辅助多分支。
- 超出 Skill 边界：无包证据且接口直达切 protocol；端行为完整且统一调度切 group_control；动态插件证据明确切 plugin_reverse。
- 工具 / API 不可用：说明无法完成哪类工件或日志分析，改用包签名分布、端 SDK 覆盖率、外部分发样本、runtime 截图和风险请求关联替代。
- 无法判断：明确说“当前不足以判断破解包”，并说明缺包样本、包签名、SDK 覆盖率、官方版本对比还是方法级短链证据。
