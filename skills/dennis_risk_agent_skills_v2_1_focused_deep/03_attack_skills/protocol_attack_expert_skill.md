# Protocol Attack Expert Skill：协议攻击专项专家 Skill v2.3 executable-deep

## 0. Skill 定位

本 Skill 解决“请求是否脱离正常端侧执行链路、是否为协议攻击、是哪类协议、如何补证和治理”的问题。

不解决：有完整端行为但统一调度的群控、客户端被改造导致采集缺失的破解包、真人任务化执行、合法自动化授权管理本身。遇到这些情况应切换或组合 group_control_expert_skill、cracked_app_expert_skill、real_user_crowdsourcing_skill、risk_governance_design_skill。

## 1. 触发条件

- 关键词触发：协议攻击、接口直打、无端请求、接口重放、签名绕过、参数构造、token 复用、强目标接口、前后端冲突、SDK 缺失、接口序列异常。
- 业务场景触发：反爬接口直取、登录接口滥用、活动领奖接口直达、未登录态接口获取核心资产、token 跨环境使用。
- 用户意图触发：用户问“是不是协议”“怎么区分协议和群控/破解包/真人”“怎么补证协议”“接口怎么治理”。
- 反向不触发：只有高频请求、IP 聚集、访问量上涨，或只有“服务端有请求、前端无日志”时，不直接触发强协议结论；必须先排除埋点缺失、SDK 采集、网关采样、版本差异、破解包绕采集和合法自动化。
- 需要转交给其他 Skill 的情况：
  - 有完整端行为但同批调度、节奏/路径/收益成团：转 group_control_expert_skill。
  - 包签名、SDK、hook、root、采集绕过异常明显：转 cracked_app_expert_skill。
  - 接口化调用、批量登录、自动化运营中存在授权工具、官方工具、商家/达人/MCN/机构合理调用：先引用 `06_templates/legal_operation_matrix_playbook_v2_3.md` 做合法矩阵前置判断。
  - 真人任务平台或人工验证：转 real_user_crowdsourcing_skill。

## 2. 输入格式

- 必需输入：目标接口/业务动作、服务端请求日志、端侧事件链或前端埋点、token/设备/IP/UA/SDK 关联信息。
- 可选输入：签名字段、参数生成链路、App 版本、SDK 日志、登录/刷新 token 日志、页面路径、业务收益链路、合法授权清单。
- 缺失时可默认假设：用户只问概念时，默认输出协议本质、证据分层和最小补证动作。
- 缺失但不可假设时如何处理：缺少前后端 join 或端侧事件链时，不做强协议定性，只输出补证动作。
- 用户只给模糊问题时的最小可用输入：接口、端侧链路、token/设备一致性、请求序列、是否命中强目标动作。

## 3. 专家认知

- 这类风险的本质：协议攻击是业务请求脱离正常端侧执行链路，通过脚本、接口重放、参数构造、签名破解、token 复用等方式直接请求服务端。
- 黑产 / 风险动机：降低端侧成本，绕过页面路径、验证、频控、设备校验和业务规则，直接命中强目标接口完成收益或资产获取。
- 主要风险形态：
  - 单纯协议：无真实端行为，直接请求。
  - 养设备协议：有设备身份，但行为链不真实。
  - Token 复用协议：token 与设备/IP/环境冲突。
  - 签名绕过协议：签名复用、参数构造异常。
  - 混合协议：真人/群控前置，后续协议化。
  - 合法接口滥用：有业务自动化需求，但调用边界异常。
- 常见混合形态：群控前置 + 协议领奖，真人验证 + 协议提现，破解包绕采集 + 协议接口直达，token 泄露 + 协议复用。
- 和相近风险的区别：
  - 群控：群控通常有端行为但调度异常；协议重点是无端链路或端链路不真实。
  - 破解包：破解包是客户端改造；协议是服务端请求链路脱端，两者可混合。
  - 合法自动化：合法自动化有授权、审计和业务合理性；协议攻击规避平台规则获利。

## 4. 判断规则

按顺序判断，命中即进入对应分支；证据不足时不得强结论。

1. 如果服务端请求无对应页面/事件链，接口调用顺序不符合正常 App 路径，强目标接口直接命中，且参数/签名/token/设备链路存在端生成缺失或冲突，则判断为高置信单纯协议，需要输出前后端冲突证据、反证和接口治理。只有“前端无日志”单点时，只能判断为前后端链路冲突，先排除埋点缺失、SDK 采集、网关采样、版本差异、破解包绕采集和合法自动化。
2. 如果有设备身份但冷启动、初始化、页面曝光、点击链路缺失或不真实，则判断为养设备协议，需要补 SDK 日志、设备日志、接口序列和上游路径。
3. 如果 token 与设备/IP/UA/SDK/环境冲突，且无登录/迁移/刷新合法链路，则判断为 token 复用协议，需要组合账号安全 Skill。
4. 如果签名复用、参数时效异常、参数缺少端生成痕迹、请求可脚本稳定复现，则判断为签名绕过或参数构造协议。
5. 如果真人/群控完成前置验证，但后续批量接口化执行，则判断为混合协议，需要同时输出前置手法和后续协议证据。
6. 如果端行为完整且节奏真实，但设备/账号被统一调度，则切换到群控判断。
7. 如果 SDK 缺失、包签名/运行环境异常导致“像协议”，则切换到破解包判断。
8. 如果只有高频请求、IP 聚集、接口 QPS 上升，则不得定性协议，只能进入监控、补证或灰度。
9. 如果存在接口化调用、批量登录、自动化运营，但可能属于授权工具、官方工具、商家/达人/MCN/机构合法矩阵，则先引用 `06_templates/legal_operation_matrix_playbook_v2_3.md` 校验授权主体、账号范围、工具来源、操作人、调用接口、敏感动作和收益主体；有授权但超范围时进入局部违规治理，不直接定义协议攻击；无授权、规避平台规则、收益异常或接口脱端证据闭合后，再进入协议/黑产判断。

## 5. 证据体系

- 强证据：
  - 服务端请求无对应页面/事件链；
  - 接口调用顺序不符合正常 App 路径；
  - 参数缺少端生成痕迹；
  - 签名、设备指纹、UA、SDK 版本冲突；
  - token 与设备/IP/环境不一致；
  - 强目标接口直接命中；
  - 请求可被脚本稳定复现。
- 中证据：
  - 接口序列过短；
  - refresh token 或签名刷新链路异常；
  - 设备身份存在但行为链不完整；
  - 业务收益动作紧随接口直达；
  - 同脚本模板多账号复用。
- 弱证据：
  - 高频请求；
  - IP 聚集；
  - 单接口 QPS 上涨；
  - 账号画像低质；
  - UA 相似。
- 反证：
  - 端行为完整且合理；
  - 合法商家/机构自动化授权；
  - 官方工具、授权工具或合法矩阵已登记且调用范围可审计；
  - 埋点缺失或采集口径错误；
  - SDK 升级、网关采样、前端日志延迟或版本灰度；
  - 群控真机产生端行为但节奏异常；
  - 破解包绕采集导致“像协议”。
- 误判来源：前端埋点丢失、弱网重试、App 版本差异、SDK 升级、网关采样缺失、合法批处理。
- 最小补证清单：
  - 前后端 join；
  - SDK 日志；
  - 设备日志；
  - token/设备/IP/UA 一致性；
  - 签名生成链路；
  - 接口序列；
  - 上游页面路径；
  - 强目标跳转；
  - 业务收益关联；
  - 合法自动化 / 合法矩阵：按 `06_templates/legal_operation_matrix_playbook_v2_3.md` 补授权主体、账号范围、工具来源、操作人、操作目的、调用接口、敏感动作、收益主体、业务登记信息、历史违规记录。

## 7. 治理闭环

- 查数补证：前后端 join、SDK/设备日志、token/环境一致性、签名链路、接口序列、业务收益链路。
- 识别策略：无端请求、前后端冲突、接口固化、强目标直达、token 环境冲突、签名复用。
- 分层处置：
  - 高准：敏感接口强拦、token 失效、收益冻结、账号/设备联动。
  - 中准：挑战、限流、降权、延迟结算、二次验证。
  - 低准：加采、监控、灰度校验。
- 灰度策略：先覆盖敏感接口和高置信样本，再扩到同类接口；保留合法自动化白名单和审计。
- 业务协同：接口签名升级、token/设备/环境绑定、参数时效和上下文绑定、网关验签、敏感接口接入风控。
- 体验 / 误伤控制：合法自动化授权登记、低风险请求不强拦、异常只在敏感动作 step-up。
- 指标评估：协议发生量、漏过量、无端请求占比、前后端冲突率、接口固化命中、误伤率、客诉、黑产迁移到群控/真人比例。
- 样本回流和复盘：沉淀协议样本、接口风险分级、签名绕过模式、token 复用模式、合法自动化审计规则。

## 8. 禁止行为

- 禁止因为高频请求直接判断协议。
- 禁止因为服务端有请求、前端无日志直接判断协议。
- 禁止把授权工具、官方工具或合法矩阵的接口化运营直接定义为协议攻击。
- 禁止把反爬直接等同协议。
- 禁止忽略群控、破解包、真人众包和合法自动化反证。
- 禁止证据不足强结论。
- 禁止只输出接口签名升级，不讲上下文、灰度和业务影响。
- 禁止编造真实表名、字段、SQL。

## 9. 质量校验

输出前自查：

- 是否说明“脱离端侧执行链”这一最小区分点？
- 是否识别协议分型？
- 是否完成前后端 join 补证设计？
- 是否列出端行为完整、合法自动化、埋点缺失、群控/破解包反证？
- 是否把“前端无日志”单点降级为链路冲突，并先排除采集、版本、网关和破解包问题？
- 是否说明何时切换到群控、破解包或合法自动化？
- 是否给出接口、token、签名、网关、敏感动作的治理闭环？
- 是否有误伤控制和指标？

不合格时必须补齐后再输出。

## 10. 失败处理

- 信息不足：降级为“疑似协议方向”，列前后端 join 和一致性补证清单。
- 证据冲突：输出协议/群控/破解包/合法自动化多分支。
- 超出 Skill 边界：切换或组合 group_control、cracked_app、crowdsourcing、account_security、anti_crawler Skill。
- 工具 / API 不可用：说明缺少哪类日志或 join，给离线抽样、SDK 日志、网关日志替代路径。
- 无法判断：明确说“当前不足以判断协议”，并说明缺端侧链路、签名链路还是 token 环境证据。
